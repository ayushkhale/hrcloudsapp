## 4. The keyboard — BUILT, WANTS A DEVICE CHECK

### The root cause, which is the important part

This was **not** a per-screen bug, which is why the user saw it "in whole app".

`android/gradle.properties` has `edgeToEdgeEnabled=true` (RN 0.87's default).
**With edge-to-edge, Android no longer resizes the window for the keyboard** —
the app draws behind the system bars, the window keeps its full height, and the
keyboard arrives as an *inset over the top of it*. So
`android:windowSoftInputMode="adjustResize"` in `AndroidManifest.xml` is
**inert**.

And half the comments in this repo relied on it. `ui/Screen.jsx`,
`ui/FormSheet.jsx`, `ui/ReasonPrompt.jsx`, `MayaSheet.jsx` and
`TaskDetailScreen.jsx` all said some version of *"iOS needs the padding;
Android's adjustResize already handles it, and doing both double-shifts"*. That
**was** true. It stopped being true when edge-to-edge went on, and nobody
updated the comments — so every field in the bottom half of every screen went
under the keyboard with nothing scrolling.

### What was built

**`src/ui/KeyboardAware.jsx` — new, and it holds the whole diagnosis.** Read its
header before changing any of this. It exports:

- `useKeyboardInset()` → how much of the window bottom the keyboard covers (0
  when closed). iOS uses the `Will` events so layout moves *with* the keyboard;
  Android only fires `Did`.
- `useKeyboardLift()` → `{ lift, safeBottom, keyboard }` for a bottom-pinned
  element, **with the safe-area trap already reconciled**: an open keyboard
  covers the nav bar, so `insets.bottom` is already inside the keyboard height
  and padding by both leaves a white band. `safeBottom` is 0 while the keyboard
  is up.
- `KeyboardAwareScrollView` → a ScrollView that (a) adds the keyboard's height
  as scrollable room so the last field can *reach* mid-screen, and (b) **scrolls
  the focused field above the keys**, measured in window coordinates against the
  keyboard's top edge. It runs on focus *and* on the keyboard appearing, because
  at focus time the keyboard has no height yet and at keyboard time the focused
  field may have changed. **The ref it forwards is the ScrollView's own**, so
  `hooks/useFormFocus.js` and §11's travel-to-the-first-problem keep working
  unchanged.
- `useKeyboardAware(ref)` → the same behaviour for a scroller it doesn't own.
- `useReveal()` → the context function `TextField` calls from `onFocus`.

**Wired in — two shells cover almost the whole app:**

| File | What changed |
|---|---|
| `src/ui/Screen.jsx` | the scroll case is `KeyboardAwareScrollView`; the pinned `footer` lifts by `marginBottom: lift`. **The `keyboard` prop is now ignored** (kept so callers compile) — a scrolling Screen is always keyboard-aware. This covers every auth screen, since `AuthScreen` wraps `Screen` |
| `src/ui/FormSheet.jsx` | `KeyboardAvoidingView` → plain `View`; body is `KeyboardAwareScrollView`; footer lifts. **This covers all seven form screens** (ApplyLeave, CorrectionForm, UploadDocument, BankAccount, ClaimForm, DeclarationForm, RegisterDevice) **plus** RenameDeviceSheet, EditProfileSheet and SubmitTaskSheet, which are all FormSheets |
| `src/ui/TextField.jsx` | reports its own focus via `useReveal()`, **once, here** — the alternative was an `onFocus` on forty call sites and the one you forget is the bug. A caller's own `onFocus` still runs, after ours |
| `src/ui/CodeInput.jsx` | the hidden OTP input reveals itself too (58pt boxes sitting low on the screen) |
| `src/ui/ReasonPrompt.jsx` | it **autofocuses**, so the keyboard was always up and the box always under it. A centred dialog needs no padding trick — the keyboard's height comes off the bottom of the area it centres in and it re-centres itself |
| `src/ui/Select.jsx` | the picker's search field is at the *top* of the sheet so it was never hidden; the **list** below it gets its height back as scrollable room |
| `src/features/maya/MayaSheet.jsx` | composer lifts |
| `src/features/tasks/screens/TaskDetailScreen.jsx` | `KeyboardAvoidingView` (with a hand-tuned `keyboardVerticalOffset`) → `View`; scroller is keyboard-aware; action bar lifts |
| `src/ui/index.js` | the four hooks exported, with a note that a *screen* shouldn't need them |

**`src/ui/SheetShell.jsx` was deliberately left alone.** Changing gorhom's
`keyboardBehavior` would reach every sheet in the app, including the fitted ones
whose height-reporting that file's header spends forty lines on. The only inputs
in gorhom sheets are picker search fields, and those sit at the top. The reason
is recorded in `Select.jsx` where the decision bites.

### What to check on a device

1. A long form — **ClaimForm** or **DeclarationForm** — tap the *last* field.
   It should scroll above the keyboard and the Submit footer should sit on the
   keys, not under them.
2. **Login / OTP** on a short phone.
3. **ReasonPrompt** (cancel a leave request with a reason) — it autofocuses.
4. **iOS**, if there's a Mac: the lift uses the `Will` events there and the
   numbers differ. The `marginBottom`-not-`padding` choice matters on both
   (padding would grow the bar and leave the button at the top of a tall block).
5. **A footer inside the tab navigator**, if you find one: `marginBottom: lift`
   measures from the Screen container's bottom, which is *above* the tab bar, so
   it may over-lift by the tab-bar height. Forms are modals so this is rare, but
   it is the known soft spot.

## 5. On-demand location tracking — ~45% DONE

The user's words: *"throughly analyze what they are, place them where they
belong to in our app, and integrate and implement it, follow design and ui of
our current theme and structure."*

### The feature in one paragraph

HR (or a reporting manager, for direct reports) asks where an employee is during
an **open shift**. The ask arrives as a **silent FCM data push**; the app reads
**one fresh GPS fix** and POSTs it back; the requester **polls** for the result.
No background GPS, no persistent tracking, **zero taps** for the employee — but
a local notification is posted every time, as transparency. Nothing is
"verified", only "reported".

### DONE

**Guides placed** (this was an explicit ask):
`NativeRef/70-reference/vendor/2026-10-23_on_demand_location_tracking_{mobile,frontend}_guide.md`
— verbatim copies of the two files from `~/Downloads`.

**`NativeRef/10-api/06-location-requests.md` — new, and it is the brief for the
rest of this work.** Read it. It is the employee-app-facing contract: the three
calls this app makes, the field tables, the error dead-ends, the three
anti-spoof rules the app can trip by accident, the consent mode the app
*cannot read*, the gating rule, the push payload, and the platform traps. It
also records where the two guides disagree (the frontend guide wins; its §7
lists what the first draft got wrong — notably **`NO_ACTIVE_DEVICE` is 422, not
404**, and the result is **polled**, not pushed over a socket).

**`src/api/notifications.api.js` — new.** `registerDevice` / `getMyDevices` /
`deregisterDevice`. Exported from `src/api/index.js`. Its header labours one
point: **this is not `features/devices`.** Two different things are called "my
devices" on this API — `/attendance/trusted-devices` is a Keystore credential
that signs a punch, this is an FCM token so the server can wake the handset.
Separate ids, separate lifecycles, neither implies the other.

**`src/api/attendance.api.js` — three methods added**, with full contract
comments: `reportLiveLocation`, `acknowledgeLocationNotice`,
`getMyLocationRequests`. The header now also records *why* the requester's half
is absent, so nobody adds `locate` here later.

**`src/features/notifications/pushDevice.js` — new.** `registerThisDevice(token)`
and `deregisterThisDevice()`. Fire-and-forget on purpose (push is never why
somebody opened the app, and a failed registration must not block a sign-in),
re-run on every sign-in and token refresh because re-posting upserts. The device
id is kept in AsyncStorage **per user** (two people, one handset) and the user id
is read from the live access token so no caller has to plumb it. `device_name`
reuses `suggestedDeviceName()` from `features/devices/deviceKey.js` and
`THIS_PLATFORM` from `deviceMeta.js` — **not re-derived** (CLAUDE.md §10).

### NOT DONE — in the order I'd do it

**(a) Call the registration. ~15 min.** Nothing calls `pushDevice.js` yet, so
no device is registered and **the whole feature is dead until this lands** (every
locate → `422 NO_ACTIVE_DEVICE`).

- `src/features/notifications/push.js` — in `setupPush()`, after
  `logToken()`, call `registerThisDevice(token)`; and in the existing
  `onTokenRefresh` handler, call it again with the new token. (`setupPush` is
  already invoked from `src/navigation/AppTabs.jsx` ~line 318.)
- `src/state/AuthContext.jsx` — in `endSession` (~line 127), `await
  deregisterThisDevice()` **before `clearSession()`**. This ordering is
  load-bearing: `request()` reads the token synchronously on its way to the
  fetch, so clearing first sends an unauthenticated DELETE.
  `deregisterThisDevice` carries its own 4 s ceiling so a dead network can't
  hold a sign-out open.

**(b) `src/features/attendance/liveLocation.js` — the service. The core.**

Export `handleLocationRequest(data)` taking the push's
`{ action, requestId, expiresAt }`:

1. Bail unless `action === 'REQUEST_LOCATION'`.
2. Bail if `new Date(expiresAt).getTime() < Date.now()` — a push after the TTL
   gets no fix and no notification.
3. **`await loadSession()` from `src/state/session.js`** — ⚠️ the background
   handler runs in a **headless JS context** with fresh module state, so the
   in-memory token cache is empty and every call would 401. `loadSession()`
   reads the Keychain and primes it. The entry is
   `ACCESSIBLE.AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, so it is readable with the
   screen locked as long as the phone has been unlocked once since boot. Bail if
   there is no session.
4. Post the transparency notification via **notifee** — channel
   `attendance_location_channel`, `AndroidImportance.HIGH`. Wording per
   CLAUDE.md §5 and the frontend guide: **"Location requested"**, body *"Your
   workplace has requested your current location."* — **requested, not
   verified**, and no "HR has…" unless you have the requester's name (you
   don't, in the push). Put the strings in `src/config/dictionary.js` if a term
   repeats. Wrap it in try/catch: a failed notification must not stop the fix.
5. Take a fix — **`maximumAge: 0`, `enableHighAccuracy: true`, `timeout: 10000`.**
   ⚠️ **Do not use `getPunchLocation()`** from `src/lib/location.js`: it
   deliberately takes a cached fix up to 60 s old first so the Clock in button
   doesn't spin, and that trips the server's `stale_fix` signal here. Add a
   *new* exported function to `src/lib/location.js` beside it —
   `getFreshLocation()` or similar, reusing the existing private
   `getPosition()` and `validCoords()` — rather than a second geolocation
   wrapper in a feature folder.
6. POST `attendanceAPI.reportLiveLocation({ … })`. `captured_at` is
   `new Date(position.timestamp).toISOString()` — the **hardware** timestamp,
   never `Date.now()`. `is_mock: position.mocked === true`. `platform:
   THIS_PLATFORM`.
7. 404 / 409 are **dead ends** — discard, never retry.

`battery_level` is **optional and I would skip it**: it needs
`react-native-device-info`, and one more native dependency for one optional
integer is a poor trade. Say so in the header rather than leaving it looking
forgotten.

**(c) Wire the push handler. Two places, both already exist.**

- `index.js` → `registerPushBackgroundHandler()` already runs at module scope
  (Firebase's rule). Inside it, in `push.js`, dispatch to
  `handleLocationRequest(msg.data)` when `msg.data?.action === 'REQUEST_LOCATION'`.
- `push.js` → `setupPush()`'s `onMessage` (foreground) must dispatch too, and

  has no `notification` block so today it shows nothing, but check.

### Things the guides get wrong or leave out — don't "fix" these back

- **`NO_ACTIVE_DEVICE` is `422`**, not 404 (mobile guide's older draft said 404).
- The result is **polled** by the requester, not pushed over SSE/WebSocket.
- **"Reported", never "Verified Live".**
- `spoof_flagged` is **absent** from `GET /attendance/locations/mine` by design.
- The guides' code samples use raw `fetch` with a hand-built `Authorization`
  header and a hardcoded `https://api.yourdomain.com`. **Everything goes
  through `api/*.api.js`** here (§6) — no `fetch` in a component, and the base
  URL comes from `config/env.js`.
- The guides are TypeScript. **This repo is plain JS/JSX.**
- The mobile guide's `apiClient.post('/api/v1/attendance/…')` includes the
  `/api/v1` prefix; `ENV.API_BASE_URL` **already ends in `/api/v1`**, so the
  paths in `attendance.api.js` are correct as written (`/attendance/locations/…`).
